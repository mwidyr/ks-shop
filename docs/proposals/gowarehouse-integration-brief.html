GoWarehouse Integration Brief

Ralulu ERP · prepared for discussion with the client · based on the Partners API 2026-09 documentation (sharedhd.gowarehouse.ai/partners/docs/en/2026-09) and the current ERP code. No live API call has been made yet (no token).

1. Summary

GoWarehouse (GW) offers a REST API for products, orders, shipments, inventory, inbounds and returns. Our ERP already has a Shipping Workbench with a 3PL stage, but that stage is manual today: staff download a packing Excel and later upload a confirmation file, and neither file format is final. The GW API can fill exactly these two gaps.

Proposal
  1. Phase 1: SKU sync (ERP to GW) and a “Send to GoWarehouse” button in the Shipping Workbench batch page, replacing the packing-Excel download for the 3PL.
  2. Phase 2: pull shipment status and tracking numbers from GW and use them to confirm shipment automatically (replacing the 3PL confirmation upload).
  3. Later / manual for now: inventory comparison, inbound (from Procurement Orders), returns.
Existing ERP logic (eligibility, batches, platform export and import, stock rules) stays unchanged. The new code only adds an alternative path for the two 3PL steps.

Decisions we need first: (a) whether GW prints the 7-Eleven / FamilyMart / HCT labels we already create, or creates its own carrier shipment; (b) the codes and formats GW expects (section 5).

2. How the ERP works today (from the code)

1. New orderstatus pending
2. Eligible & batchShipping Workbench checks the rules, staff create a batch
3. Platform exportExcel to 7-Eleven / FamilyMart / HCT → processing
4. Platform result importplatform order no. + shipping no. → ready_to_ship
5. 3PL packing fileExcel downloaded by staff (placeholder format)
6. 3PL shipment confirmationExcel uploaded by staff (parser not built, format unknown)
7. Shippedstock deducted, status shipped
8. Deliveredplatform delivery import → delivered

Highlighted boxes (5 and 6) are where GoWarehouse would plug in.

Eligibility rules (computeEligible in shipping_batches.go)

  • Order status pending, not already in a batch, delivery provider matches (7-Eleven, FamilyMart or courier).
  • Created before 00:00 Taiwan time today (UTC+8), so same-day orders wait.
  • Kept orders are held until 1 day (shipping date mode) or 4 days (expected delivery mode) before their kept date.
  • Each shipment is classified ready / problem / insufficient stock; physical stock is allocated oldest first and never promised twice. Unknown store codes are flagged.
  • Orders merged into one shipment are batched as a whole.

Stock model (stock_calc.go, order_status.go)

  • Actual (physical stock) only drops when an order moves to shipped, which happens when the 3PL shipment is confirmed. Creating, batching, exporting or cancelling never touches it.
  • Ordered is derived from orders in pending / processing / ready_to_ship, so it cannot drift. Available = Actual + Incoming − Ordered.
  • Every status change goes through one function (applyStatusChange), so stock, promo, wallet and points side effects stay consistent.

Data we already have

  • SKU: product_variants.sku (unique, up to 60 characters), one per colour/size variant.
  • Order fields: order number, customer name / phone / address, pickup chain and store code, platform_order_no, tracking_number, shipping fee, exported_at, and the keep date with its type.
  • Logs: order_export_log (what was exported, when) and shipping_import_log / issues (what was imported and what could not be matched).

What is manual or unfinished today

  • The 3PL packing Excel is a placeholder “until the 3PL confirms its real format” (excel.js).
  • The 3PL shipment-confirmation and delivery parsers refuse to guess formats (parsers.js); the backend rules for applying them already exist.
  • Products are created only inside the ERP, with no warehouse catalogue to keep in sync.

3. What we learned from the GW API

TopicWhat the documentation says
AccessBase path /api/partners/2026-09. Bearer token per integration, with scopes per endpoint (e.g. products:write, orders:write). The token can be restricted to an IP allowlist.
Limits180 requests / minute, 10 / second, and 10,000 / day per merchant. Throttled calls return 429 with Retry-After. This is comfortably enough for our order volume.
FormatFlat JSON bodies (no wrapper), money and weights as strings, dates YYYY-MM-DD, timestamps in UTC, cursor pagination (page_size, since_id, has_more) and updated_at_min filters for incremental sync. Errors are machine codes (e.g. validation_failed).
Webhooks9 events: order.created, order.shipped, order.cancelled, shipment.shipped, shipment.status_changed, inventory.updated, inbound.completed, return_receipt.verified, return_order.received. Signed with a secret; requires a public HTTPS endpoint. Polling is a valid alternative.

Things that affect our design

  • If an order contains an SKU GW does not know, GW silently creates an “UnknownProduct” and still accepts the order, unless strict mode is enabled for the merchant. So SKU sync must come first.
  • inventory_type is required on every order item and must exist in GW (the docs mention values like normal, damaged and expired).
  • An order can only be edited in GW while it is still pending; after that it can only be cancelled (irreversible).
  • Shipments cannot be created through the API, so tracking and status always come from GW.
  • The API does not expose a field specifically for a carrier tracking number on the order we send. We can pass our platform order number and shipping number in extra_name or note, but this must be agreed with GW.

Minimal ERP changes

  • One GW client module (token and base URL in settings, never in the repository).
  • New columns: gw_order_id and gw_sent_at on orders, gw_synced_at on variants, and one sync-log table.
  • Safeguards: an order with a GW id cannot be sent twice; rate-limit and error handling with retry; every send is logged with the user who triggered it.
  • Nothing is removed. The Excel path stays available as a manual fallback.

5. Questions for the client and GoWarehouse

Each question has our recommended answer, so the client can simply confirm or correct it.

#QuestionOur recommended answer
1Labels: does GW print the 7-Eleven / FamilyMart / HCT labels created through our platform step, or does it create its own carrier shipment and tracking?Keep our platform step (least change) and pass the platform order and shipping numbers to GW. If GW creates its own shipments, the platform export step may become redundant and we should redesign. Needs GW’s answer first.
2Codes: which inventory_type, warehouse name and shipping_type codes should we send for 7-Eleven, FamilyMart and home courier?Ask GW for the exact list. We store them as settings, not in code. We expect normal for sellable stock but have not confirmed it.
3Store code: which format does convenience_store_code expect?Our 6-digit store codes; GW to confirm. We can convert if they differ.
4Strict SKU mode and sandbox: can strict mode be enabled, and is there a test merchant?Yes to strict mode, so unknown SKUs are rejected instead of silently accepted. Test in a sandbox first; if none exists, test with one low-value real order.
5Stock ownership: when does stock go down?Keep today’s rule: ERP Actual drops when the order becomes shipped (GW confirmed), and GW stock is shown for comparison only. This avoids deducting twice.
6Merged shipments: when several ERP orders ship together, how should GW receive them?Send each ERP order separately with the same note reference; GW shipments already list several order names. GW to confirm.
7Changes and cancellation: what happens if a customer cancels after we sent the order?The ERP already locks orders after export. If GW is still pending we call cancel; after that it is a manual case with GW.
8Kept orders: should GW hold orders until the kept ship date?No. The ERP already holds them and only sends when they are due; scheduled_shipping_date is optional.
9Webhooks: do we use webhooks or polling for shipment updates?Start with polling every 10–15 minutes (no public endpoint needed), add webhooks later.
10Access: IP allowlist and token scopes.Register our production server IP. Scopes: products:read/write, orders:read/write. Add inventories:read, inbounds:write, return_orders:read only when those phases start.
11Returns and invoices: who receives returned goods, and does GW issue invoices?Returns handled manually first; invoices skipped unless GW issues them.

6. What we have not verified
